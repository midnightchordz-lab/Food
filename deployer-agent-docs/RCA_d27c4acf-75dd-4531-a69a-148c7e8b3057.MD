# RCA — "Payment could not be completed" on Android trial activation

App: app-launch-2905 (MoodFood) · DB: `app-launch-2905-moodfood_production`
Active/live run inspected: `d27c4acf-75dd-4531-a69a-148c7e8b3057` (redeploy, success, promoted 2026-09-24 07:18Z)

## TL;DR
The deployed **backend source and frontend source both contain the fixes** you just made. The bug is caused by THREE independent problems, none of which is "the deploy didn't ship the code":

1. **(Backend gap — primary root cause of "new user has no trial")** Google & Apple OAuth signup routes never call `auto_start_trial_if_eligible`. Only email/password `/register` and phone OTP do. Every recent new user signed up with Google → no trial fields, no `user_subscriptions` doc → not premium.
2. **(Client build — why activate is never tried)** Production access logs show **zero** `POST /api/trial/activate` calls, while `POST /api/subscription/razorpay/create-subscription` is hit directly. The new `paywall.tsx` (which calls `/trial/activate` first, unconditionally) is in the deployed **source** but the **installed Android APK the user is running is an older native build** that goes straight to Razorpay.
3. **(Razorpay config — why the fallback itself errors)** Every `create-subscription` fails with `Razorpay subscription error: Authentication failed` → the stored RAZORPAY key/secret is rejected by Razorpay (wrong keys or test/live mismatch). This is what actually produces the "Payment could not be completed" toast.

### D) Root cause of auto-start not happening at signup
It is **NOT a swallowed exception** in `auto_start_trial_if_eligible`. It is that the OAuth signup paths never invoke it:
- `grep auto_start_trial_if_eligible routes/google_auth.py routes/apple_auth.py` → **no matches** (exit 1).
- `routes/google_auth.py` `POST /session` (lines 26–77) inserts the new user with `trial_active:False` and returns — no auto-start call.
- `routes/apple_auth.py` `POST /apple` (lines 46–104) — same.
- Only `routes/auth.py` `/register` (line 109) and phone OTP verify (line 329) call it.

### E) Razorpay path
`RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are present (not empty) in deployment secrets; `RAZORPAY_WEBHOOK_SECRET` is empty. Razorpay's API rejects the credentials at auth (`Authentication failed` on every create-subscription). Values exist but are wrong/rejected — likely test-vs-live mismatch, revoked, or key/secret don't pair. (Secret values are never exposed to me; this is inferred from the repeated auth failures.) Per product intent a genuine trial user should never reach this path — but as long as the client skips `/activate`, this failure is exactly the toast the user sees.

## Fixes (for E1 to apply in source, + one user action)

1. **Backend (source):** In `routes/google_auth.py` `/session` and `routes/apple_auth.py` `/apple`, after creating a new user (`is_new_user`), call `await auto_start_trial_if_eligible(user_id, platform)` — mirror `routes/auth.py:109`. Import it from `.trial`. This makes OAuth signups get the 7-day trial + `user_subscriptions` doc like email/password signups. (Existing Google users already registered can also be healed by the `/activate` self-heal / step-3 once the client calls it.)

2. **Android client (rebuild):** The deployed `paywall.tsx` already calls `/trial/activate` first, but the APK in the user's hands predates it (zero `/activate` calls in prod). After the backend deploy, **regenerate the Android build** (Publish to Play Store → Generate Build) so the shipped binary includes the activate-first paywall. Razorpay uses a native module, so this must be a real native build, not just an OTA.

3. **User (config):** Verify/rotate `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` (and set `RAZORPAY_WEBHOOK_SECRET`) in Deployment Panel → Secrets → Save → redeploy. Confirm they are live-mode keys that pair correctly. This clears `Authentication failed`.
